# 自动云备份技术方案

日期：2026-08-08  
状态：方案草案

## 1. 需求定义

本方案中的“同步”是指：应用自动把客户业务数据备份到用户指定的云盘，并可从云盘下载后恢复。

它不做两台设备同时编辑后的数据合并，也不追求秒级实时同步。采用“本地数据库为主、云端保存版本化备份文件”的方式即可。

## 2. 推荐结论

首选 **WebDAV 自动备份**。

原因：

- 协议简单，上传、下载、列目录、删除旧文件都有标准 HTTP 方法。
- App 只需实现一次 WebDAV 客户端，可对接坚果云、Nextcloud、ownCloud、群晖及其他提供 WebDAV 的存储。
- 不需要为每家网盘分别维护 OAuth、SDK 和应用审核。
- 当前项目已经能生成完整 ZIP，新增工作主要是上传和设置页面。

若目标网盘没有 WebDAV，再按实际用户选择接入其官方 API。不要首版同时支持多家云盘。

## 3. 方案对比

| 方案 | 接入成本 | 适用场景 | 注意事项 |
|---|---:|---|---|
| WebDAV | 低 | 坚果云、Nextcloud、群晖等 | 首选；通常使用服务器地址、用户名和应用密码 |
| S3 兼容存储 | 低至中 | OSS、COS、MinIO 等 | 稳定，但更像对象存储；长期密钥不宜直接放 App，可用受限凭证 |
| OneDrive Microsoft Graph | 中 | 已使用微软账号 | 需要 OAuth 登录、token 刷新和应用注册 |
| Dropbox API | 中 | 海外用户 | 需要 OAuth，国内网络可用性需实测 |
| 百度网盘/阿里云盘官方 API | 中至高 | 指定国内网盘 | 依赖开放平台权限、OAuth、审核和接口限制，开发前需核对当期政策 |
| 系统分享至网盘 | 极低 | 手工备份 | 当前已有，但不能无人值守自动上传 |

不建议通过第三方非官方接口或模拟登录上传网盘，容易因验证码、风控或接口变化失效，也有账号安全风险。

## 4. 复用现有能力

当前 `BackupRestoreService` 已经生成完整 ZIP，内容包括：

- `customer.sqlite`：可直接完整恢复的数据库。
- `data.json`：全部业务表的可读快照。
- `attachments/`：应用私有附件。
- `manifest.json`：schema 版本、文件列表和 SHA-256 校验和。

因此无需改客户、联系人、项目等业务表。只需把现在的 `backupAndShare()` 拆成：

```text
createBackup() -> BackupArtifact(file, fileName, size, sha256)
shareBackup(artifact)
uploadBackup(artifact, cloudProvider)
```

手工分享和自动云备份共同调用 `createBackup()`，避免生成逻辑出现两套实现。

## 5. 客户端设计

### 5.1 云存储抽象

```dart
abstract interface class CloudBackupProvider {
  Future<void> testConnection();
  Future<void> upload({required File localFile, required String remoteName});
  Future<List<RemoteBackup>> listBackups();
  Future<File> download(RemoteBackup backup);
  Future<void> delete(RemoteBackup backup);
}
```

首版仅实现 `WebDavCloudBackupProvider`。以后增加 OneDrive 或其他网盘时，不改备份业务逻辑和页面流程。

### 5.2 WebDAV 上传流程

1. 生成本地 ZIP 临时文件并完成 SHA-256 计算。
2. 确保远端目录 `/客户跟进助手/备份/` 存在。
3. 先上传为 `文件名.uploading`。
4. 上传完成后检查远端大小；条件允许时再校验服务端 ETag。
5. 使用 WebDAV `MOVE` 原子改为正式 `.zip` 文件名。
6. 更新本地最近成功时间，并按保留策略清理旧版本。

临时名称可以避免断网时留下一个看似可恢复、实际已损坏的 ZIP。

建议文件名：

```text
customer-backup_20260808_153000_device-ab12.zip
```

### 5.3 触发策略

MVP 不必监听每一次客户字段变化立即上传，采用合并触发更可靠：

- 用户打开 App 后，距离上次成功备份超过 24 小时则后台上传一次。
- App 从后台回到前台时检查一次。
- 用户可在设置页点击“立即备份”。
- 有数据变化才备份：保存本地 `dataRevision`，成功上传后保存 `lastBackedUpRevision`；两者相同则跳过。
- 同一次运行中连续修改只生成一次备份，建议延迟 5 分钟合并。

若必须在 App 未打开时每天自动执行，再增加 Android WorkManager。系统和 ColorOS 可能延迟后台任务，所以 UI 文案应是“系统允许时自动备份”，不能承诺固定时刻完成。

### 5.4 保留策略

建议默认保留：

- 最近 7 个每日版本。
- 最近 4 个每周版本。
- 用户手工创建并标记保留的版本不自动删除。

更简单的 MVP 也可只保留最近 10 个版本。先成功上传新版本，再删除旧版本。

## 6. 设置页面

增加“自动云备份”区域：

- 启用自动备份开关。
- 服务类型：首版固定 WebDAV。
- 服务器地址、用户名、应用密码、远端目录。
- 是否包含附件；默认包含。
- 仅 Wi-Fi 上传附件开关。
- 最近成功时间、最新文件名和最近错误。
- 测试连接、立即备份、查看云端备份、恢复。

恢复仍复用现有 ZIP 校验和 `stageRestore()` 流程：从 WebDAV 下载到本地临时目录，通过现有完整校验后才进入恢复。

## 7. 安全要求

- WebDAV 密码或 token 使用 Android Keystore 支持的安全存储，不能写入当前明文 `prefs.json`。
- 只允许 HTTPS；默认拒绝明文 HTTP 和无效证书。
- 当前 ZIP 未加密，云盘服务商可以读取其中的客户信息。正式上线自动上传前，建议给 ZIP 外层增加 AES-256-GCM 加密。
- 加密密码不能与 WebDAV 密码混用；需要提示用户妥善保存恢复密钥。遗失密钥后云端备份无法恢复。
- 日志只记录状态码和错误类型，不记录用户名、密码、客户内容或完整签名 URL。

如果首版暂不做客户端加密，应在开启页面明确提示“云端备份未加密”，并只允许用户主动确认后开启。

## 8. 网络与失败处理

- 上传超时或断网不影响本地保存，临时文件保留供下次重试或安全清理。
- 使用指数退避重试，单次运行最多重试 3 次，避免持续耗电。
- 对 401/403 停止自动重试并提示重新配置凭证。
- 对空间不足、配额超限、证书错误给出明确状态。
- 同一备份使用稳定操作 ID，重试前先检查同名正式文件是否已存在。
- 下载后必须运行当前备份服务已有的 schema、SQLite、附件路径和 SHA-256 校验。

## 9. 最小实施范围

### MVP（约 3 至 5 个工作日）

1. 拆分备份文件生成与系统分享。
2. 增加 HTTP/WebDAV 客户端和连接测试。
3. 实现上传、远端列表、下载和删除。
4. 增加设置页、凭证安全存储和“立即备份”。
5. 增加每日一次的前台自动触发、失败重试和最近状态。
6. 复用现有恢复校验完成云端恢复测试。

### 后续增强

- Android WorkManager 后台定时任务。
- AES-256-GCM 客户端加密。
- 仅 Wi-Fi、充电时上传、版本保留策略。
- OneDrive 或指定国内网盘官方 API。
- 不含附件的小型高频备份，加上含附件的低频完整备份。

## 10. 推荐落地顺序

首版采用：**WebDAV + 完整 ZIP + 每日/手工触发 + 最近 10 个版本 + 现有校验恢复**。

这条路线不动业务数据模型，改造集中在备份服务、云存储适配器和设置页。它满足客户资料自动上云与换机恢复，同时保留当前完全离线使用方式。
